# Phase 22 — Fix: streaming proxy silently dropped all reasoning tokens

## Goal
Root-cause and fix "Pi Coding Agent stopped after getting a response" —
diagnosed as a severe, previously-undetected bug in the OpenAI-compatible
streaming proxy: every reasoning/thinking token generated by the model was
being silently discarded, never forwarded to the client and never counted
in the conversation log.

## Why
Investigating a live incident (`task 11` in `turboquant.2026-08-29.log`,
2026-08-28 23:xx–00:46): a request logged `completion_tokens=16384`
(hit `max_tokens`) but the conversation logger's captured `response` text
was only 4,255 characters — a ~0.26 chars/token ratio, far below normal
English/code (~3.5-4.5 chars/token) and with **zero** `<think>` tags
present. The visible content was a `write` tool-call attempt (a large plan
document) that got cut off mid-JSON, unparseable by Pi — consistent with
"stopped after getting a response."

Live-verified the root cause directly: `curl`'d llama-server's raw
streaming endpoint (port 7433) and confirmed it reports reasoning via a
**separate, structured `delta.reasoning_content` field** on each SSE chunk
— not embedded `<think>` tags in `delta.content` the way its *non-streaming*
endpoint does (confirmed and documented back in phase-14's
`non_streaming_response`/`split_reasoning` comment, which is correct for
that endpoint). `src/server/proxy.rs::spawn_event_reader` — the SSE
consumer for every streaming request — only ever read
`delta.content` and never checked `delta.reasoning_content` at all, so
every reasoning token was silently discarded: never forwarded as any
`GenerateEvent`, never reaching `response_buf`, never logged, and never
sent to the client — not even as a "thinking" indicator. A trivial live
test (`"What is 17*24?"`, `max_tokens=80`) reproduced it instantly:
TurboQuantLoader's own `/v1/chat/completions` returned two chunks with
empty `content` and `finish_reason: "length"` — the entire 80-token budget
had gone to reasoning, and the client received nothing.

This explains essentially every "reasoning ate the whole budget and the
client got nothing" symptom chased earlier in this investigation
(2026-08-25's coding-agent findings, phase-70 in that repo) — those were
real, but the diagnosis stopped one layer too shallow: the model wasn't
just "spending too much budget on reasoning," our own proxy was actively
throwing that reasoning away before it ever reached a client, so there was
no way for any client (Pi, the coding-agent, or a human) to see it happening
or react to it.

## Files Modified
| File | Change |
|------|--------|
| `src/model/backend.rs` | Added `GenerateEvent::Reasoning(String)` variant, distinct from `Token`. |
| `src/server/proxy.rs` | `spawn_event_reader` now also reads `delta.reasoning_content` and forwards it as `GenerateEvent::Reasoning`. `spawn_tracked_reader` counts it toward TTFT/token metrics the same as `Token` (TTFT was previously measuring time-to-first-*content*, silently wrong for any reasoning-heavy response). |
| `src/server/routes/openai.rs` | New `GenerateEvent::Reasoning` arm in the streaming handler: appends to `response_buf` (so conversation logs capture the true full response again) and emits it directly as a `reasoning_content` delta chunk to the client — bypassing the `StreamParser`'s `<think>`-tag detection entirely, since this field already arrives cleanly separated and was never tag-encoded to begin with. |
| `src/server/routes/anthropic.rs` | New arm folds `Reasoning` into the same handling as `Token` (visible text) — the Anthropic Messages API has its own native "thinking" content-block type; wiring that up properly is out of scope here, this just stops the silent data loss. |
| `src/inference/stream.rs`, `src/main.rs` (×2 sites) | `collect_full`/REPL/`bench` — folded `Reasoning` into the same handling as `Token` (appended to accumulated text, or ignored where `Token` was already ignored). |

## Behavior Changes
- OpenAI-compatible streaming clients (Pi, the coding-agent, anything else)
  now actually receive `reasoning_content` deltas as the model thinks,
  instead of dead air followed by either real content or an empty
  `finish_reason: length`.
- Conversation logs (`conversations.<date>.jsonl`) now capture the true
  full response including reasoning text, restoring the char/token
  correspondence that was silently broken before.
- TTFT metrics for reasoning-heavy responses will now report accurately
  (time to first *token of any kind*), likely showing much lower TTFT
  values than previously logged for the same requests.

## Assumptions & Risks
- Not yet deployed to the live binary (same file-lock constraint as
  phase-21 — the running process holds `target/release/turboquant-loader.exe`).
  Verified via `cargo check`/`cargo test`/`cargo clippy` and a live `curl`
  against the *current* (unpatched) binary confirming the raw upstream
  behavior this fix targets; full end-to-end re-verification against the
  patched binary is still needed after deployment.
- The Anthropic route's handling (folding reasoning into visible text) is a
  minimal, non-breaking stopgap, not a proper "thinking" content block —
  flagged in a code comment for whoever picks up Anthropic-side parity
  later.
- Does not change model/reasoning_effort behavior at all — a request can
  still spend its entire `max_tokens` budget on reasoning. What changes is
  that the client can now *see* that happening in real time (via
  `reasoning_content` deltas) instead of it being invisible, which should
  make future diagnosis of budget-related stalls immediate rather than
  requiring log archaeology like this investigation needed.
